## 二、第⑥项：图片错配根因说明（基于证据，非预设）

### 现象复盘（任务书）
1. 涂山容容图跳串：删除重建容容后，前一张图跑到容容名下；
2. 放图时前一张图直接"复制"到新角色页面；
3. 刷新后容容图消失（引用失效）。

### 根因（物理层）：浏览器默认流水文件名 + 同名覆盖/误引用
用户从网页保存图片时，浏览器默认命名为 `images.jpg`、`images_1.jpg`、`images_2.jpg`……**每次保存都会重名**。项目 images/ 目录中存在大量此类命名（仅兽耳娘就有 images_1/3/4/5/6/7/12~32 等 20+ 个）。当"放图"（手动复制或上传）到 `images/兽耳娘/` 时：
- **手动放图同名 → 直接覆盖旧文件**：旧角色的引用路径不变，但文件内容换成了新图 → 旧角色页面显示新角色的图（"图跳串"）；
- **新角色引用了已存在的同名文件 → 显示的是前一个角色的旧图**（"前一张图复制到新页面"）。

**证据链：**
1. 历史备份 `index.html.bak-20261027-撤回错图前`（v35）中，涂山容容（当时 id=245）的引用是 `兽耳娘/images_2.jpg`；
2. 该 `images_2.jpg` 现存于 `.creative-design/撤回错图/`，目检为**紫黑裙长发角色，绝非容容**（容容为绿发狐耳）——即 v35 时容容名下挂的就是串来的错图，后来被撤下；
3. 撤回错图目录中 `1645599886520.jpg`、`bcac40ec…jpg` 与现役涂山红红引用的同名文件 **md5 完全相同**——同一批默认命名图片被多处复制/引用的直接物证；
4. 恢复后的容容（现 id=286）引用 `兽耳娘/images_7.jpg`，目检确认**就是容容本人**，当前无错配。

### 根因（机制层，两个加重因素）
1. **上传与引用非原子**：原 `processFiles` 并发上传 + `done` 计数含非图片文件 bug；上传成功但 `save()` 失败被 `.catch(()=>{})` 静默吞掉时，图片已落盘、引用却没写入 index.html → 磁盘孤儿 + "挂不上图"。**椰子即实例**：`椰子_1.png/椰子_2.png` 在磁盘上是孤儿（上传成功），而数据里的引用是另两个 ~tplv 文件名——"椰子的图挂不上"由此而来。
2. **`/upload` 同名加 `_1` 流水后缀**：无意义且不可追溯，同一角色的图散落多个流水名，进一步放大同名混淆。

### 已实施的修复
1. **server.py /upload 文件名强化**：前端上传时携带角色名，服务器按 `角色名_YYYYMMDD_HHMMSS_序号.扩展名` 生成唯一可追溯文件名；浏览器默认流水名（images/img/下载/未命名/截图/纯数字等）一律替换为生成名；扩展名白名单校验。实测：`my-art.png` → `兽耳娘/自检测试角色_20261027_052458.png`，`images.jpg` → 同样被生成名替换。
2. **前端 processFiles 重写**：串行上传（严格保持选择顺序）→ 每张成功才 push 引用（上传↔引用一一对应）→ 全部完成后统一 save；失败的明确提示且不写入图鉴（不再静默降级 base64 塞爆 localStorage）；非图片文件计数 bug 修复。
3. **现存错配修正**：椰子（id=285）挂上 `兽耳娘/椰子_1.jpg`（日常装）、`椰子_2.jpg`（女仆装），显示正常（压缩后新文件）；容容引用已正确无需改动；全量扫描共享引用 0 处——数据层"图串到别的角色"现状清零。
4. **孤儿与被替换原图**：椰子 2 张 2.5MB 原图 PNG + 2 张被换下的 ~tplv 水印图，已移入 `.creative-design/撤回错图/`（只移动未删除）。
